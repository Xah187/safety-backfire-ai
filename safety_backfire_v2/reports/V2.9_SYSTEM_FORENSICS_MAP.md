## 2. Layer-by-Layer Forensic Deconstruction

### Layer 1: Frame Decoder & Temporal Clock

* **Module:** `cv2.VideoCapture` / RTSP client wrappers (`v2_9_baseline_runner.py`, `generate_v2_8_5_video.py`)
* **Inputs:** Raw video container (MP4, H.264/HEVC) or live RTSP network stream.
* **Outputs:** BGR Image array `np.ndarray (H, W, 3)`, frame index `frame_idx: int`, timestamp `time_sec: float`.
* **Explicit Assumptions:**
  * Video has a constant frame rate (CFR).
  * Timestamps strictly advance monotonically: $t_{i} > t_{i-1}$.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * Multiple legacy experiment scripts (`run_v2_7_experiment.py`, `run_v2_8_experiment.py`, `run_v2_8_2_experiment.py`) hardcoded `video_time_sec = f_idx / 30.0` despite `test2.mp4` running at **25.0 FPS**. This introduced a systematic **$20\%$ velocity and TTC distortion** across all V2.7 and V2.8 historical reports.
  * In variable frame rate (VFR) recordings or dropped-frame RTSP streams, elapsed frame count $N$ does not match physical time, causing severe errors in $\Delta t = \Delta \text{frame} / \text{FPS}$.
* **Internal State:** File pointer, internal buffer, frame counter.
* **Dependencies:** OpenCV (`cv2`), OS video decoders (FFmpeg backend).
* **Failure Modes:**
  * Dropped frames cause discontinuous motion misinterpreted as instantaneous acceleration.
  * Variable FPS causes speed calculations ($v = \Delta d / \Delta t$) to oscillate wildly.
  * Camera disconnect / stream stall halts the clock without emitting an error state.
* **Confidence Level:** Informational only. No confidence metric emitted.
* **Fallback Behavior:** Returns `ret == False` and abruptly terminates loop. No reconnect or buffer drain logic exists.

### Layer 2: Object Detection Engine

* **Module:** `ultralytics.YOLO` (`safety_backfire_v07/runs/forklift_person_yolo26n_v07/weights/best.pt`)
* **Inputs:** Single frame image `(H, W, 3)`, input image size `imgsz=640`, confidence threshold `conf=0.15`, NMS IoU `iou=0.70`.
* **Outputs:** 2D Bounding boxes `[x1, y1, x2, y2]`, detection confidence `conf: float \in [0.15, 1.0]`, class index `cls \in {0, 1}`.
* **Explicit Assumptions:**
  * Classes are mutually exclusive: $0 = \text{forklift}$, $1 = \text{person}$.
  * Bounding box captures the full extent of the object down to the floor contact point.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **Class Inversion Vulnerability:** The model weights define `{0: 'forklift', 1: 'person'}`. However, every experiment script from V2.7 through V2.8.4 hardcoded: `"class": "person" if int(cls) == 0 else "forklift"`. This inverted forklifts into persons and vice-versa, invalidating historical claims in those stages.
  * **Chassis Hallucination:** The detector regularly hallucinates "person" boxes on forklift counterweights, roll cages, and steering columns when confidence is set low (`conf=0.15`), producing false entities (e.g. tracks P18, P89, P108).
  * **Partial Occlusion Fragmentation:** When a forklift mast cuts across a person, the detector frequently splits a single human into two disconnected boxes or loses the detection entirely.
* **Internal State:** Stateless feedforward neural network.
* **Dependencies:** PyTorch, Ultralytics engine, model weights file (`best.pt`).
* **Failure Modes:**
  * False Positives (forklift parts detected as persons).
  * False Negatives (distant or occluded workers missed below `conf < 0.15`).
  * Class flicker: Box shifts between `forklift` and `person` frame-to-frame.
* **Confidence Metric:** Softmax / sigmoid score of detector head. Often overconfident even on hallucinations.
* **Fallback Behavior:** Empties box list if no detections meet threshold.

### Layer 3: Multi-Cue Observation Integrity Gate

* **Module:** `core/observation_gate.py` (`ObservationIntegrityGate`, `ObservationDecision`)
* **Inputs:** `obj_class: str`, `bbox: list`, `keypoints: Optional[list]`, `conf: float`, `track_history: Optional[dict]`, `spatial_context: Optional[dict]`.
* **Outputs:** `ObservationDecision(validity: str, safety_eligible: bool, evidence: dict, reason: str)`.
* **Explicit Assumptions:**
  * Non-person objects (forklifts) are valid by default (`validity=VALID`, `safety_eligible=True`).
  * Humans must satisfy human geometric aspect ratios ($1.0 \le \text{height}/\text{width} \le 4.5$).
  * Hallucinations on vehicles have large boxy areas ($>100k$ px, aspect $<1.7$) with zero keypoints.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **Non-person immunity assumption:** Forklifts are bypassed without any validity check (`if obj_class != 'person': return VALID`). If a wall, shelf, or shadow is detected as a forklift, the gate permits it unconditionally!
  * **Aspect Ratio Brittleness:** A crouching, fallen, or injured person ("Man Down") has an aspect ratio $< 1.0$ (width > height). Rule 3 in `observation_gate.py` marks them as `INVALID` and `safety_eligible = False`! **A fallen worker is completely erased from safety monitoring!**
* **Internal State:** Stateless per frame, but consumes `track_history` (track age, prior pose count).
* **Dependencies:** None (pure Python / mathematical geometry).
* **Failure Modes:**
  * False Rejection (FN): Crouching / fallen / crawling workers rejected as non-human aspect ratio.
  * False Acceptance (FP): Bulky person detections on empty forklifts accepted if aspect ratio happens to be $\ge 1.0$.
* **Confidence Metric:** Qualitative discrete classification: `VALID`, `WEAK`, `INVALID`.
* **Fallback Behavior:** Defaults to `WEAK` with `safety_eligible = True` if geometry is compatible but pose is missing.

### Layer 4: Multi-Object Tracker

* **Module:** `ultralytics.trackers.byte_tracker` (`ByteTracker` configured via `bytetrack.yaml`)
* **Inputs:** Detection boxes, scores, and classes per frame.
* **Outputs:** Persistent track IDs `trk_id: int`, updated bounding boxes, association state.
* **Configuration Parameters:**
  * `track_high_thresh: 0.25`, `track_low_thresh: 0.10`, `new_track_thresh: 0.25`, `track_buffer: 30`, `match_thresh: 0.80`.
* **Explicit Assumptions:**
  * Linear constant-velocity Kalman filter motion accurately approximates object dynamics.
  * 30 frames of occlusion buffer is sufficient to bridge temporary dropouts.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * ByteTrack maintains lost tracks for up to 30 frames ($1.2$ seconds). When a real detection is lost, the Kalman filter extrapolates bounding boxes blind. If the object stopped or changed direction, the predicted box "ghosts" through walls or machinery.
  * ByteTrack associates tracks purely on 2D IoU and detection score. In dense warehouse scenes where a pedestrian crosses in front of a forklift, IoU overlap causes frequent **ID switches** and track swapping.
* **Internal State:** Kalman filter state vectors $(\mathbf{x} = [x, y, a, h, \dot{x}, \dot{y}, \dot{a}, \dot{h}])$, covariance matrices $\mathbf{P}$, track age, frame counter.
* **Dependencies:** NumPy, Lapjv / Scipy linear assignment.
* **Failure Modes:**
  * Ghost track persistence: Extrapolating boxes across regions with no physical entity.
  * ID Switch: Pedestrian ID assigned to forklift or operator.
  * Track fragmentation: Single physical entity split across 5+ sequential track IDs.
* **Confidence Metric:** Detection score fused with IoU association cost.
* **Fallback Behavior:** Low-score detections matched against unconfirmed tracks in stage 2.

### Layer 5: Track Manager & Motion State Engine

* **Module:** `core/track_manager.py` (`TrackManager`, `TrackState`)
* **Inputs:** Raw tracked objects from ByteTrack, `frame_idx`, `video_time_sec`, `calibrator`.
* **Outputs:** Augmented tracked objects with `track_state: OBSERVED | PREDICTED | STALE`, `speed_m_s: float`, `motion_state: MOVING | PARKED`, `safety_eligible: bool`.
* **Explicit Assumptions:**
  * A track with no detector observation for $\ge 5$ frames is `STALE` and must not influence risk metrics.
  * Motion speeds $> 0.25$ m/s designate a `MOVING` entity; $\le 0.25$ m/s designates a `PARKED` entity.
  * Speed $> 8.0$ m/s constitutes unphysical tracking drift.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * In `process_tracks()`, line 116:
    $$\text{speed} = 0.6 \cdot \text{prev\_speed} + 0.4 \cdot \text{raw\_speed}$$
    This exponential moving average (EMA) creates a $3$ to $5$ frame lag before a vehicle is recognized as stopped or moving.
  * Teleportation / drift threshold ($8.0$ m/s $\approx 28.8$ km/h) is very high for indoor equipment; noisy detections jumping 1.5 meters frame-to-frame ($37.5$ m/s at 25 FPS) trigger drift, but jumps of 0.3 meters ($7.5$ m/s) are accepted and pollute speed calculations.
* **Internal State:** `self.tracks: Dict[int, Dict[str, Any]]` storing history, last observed frame, last ground point, and speed.
* **Dependencies:** `core.observation_gate.ObservationIntegrityGate`.
* **Failure Modes:**
  * Ghost track persistence: If low-confidence predictions continue to be emitted by ByteTrack, `frames_since_observation` increments, but until 5 frames elapse, predictions can still influence downstream systems.
  * Premature STALE transition during sharp turns or occlusions.
* **Confidence Metric:** Binary `safety_eligible: bool` based on state and observation validity.
* **Fallback Behavior:** Marks object as `STALE` and disables `safety_eligible`.

### Layer 6: Human Pose Estimator

* **Module:** `ultralytics.YOLO("yolov8n-pose.pt")`
* **Inputs:** Whole image frame `(H, W, 3)`, confidence threshold `conf=0.25`.
* **Outputs:** 17 COCO keypoints per detected person: $[x, y, \text{conf}]$ for Nose, Eyes, Ears, Shoulders, Elbows, Wrists, Hips, Knees, Ankles.
* **Explicit Assumptions:**
  * Pose detector boxes correspond 1-to-1 with object detector boxes.
  * A 2D IoU $> 0.30$ between detector box and pose box guarantees correct identity association.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **Identity Mismatch via Greedy IoU:** If two people stand close or cross paths (e.g., operator inside cab and pedestrian outside), greedy IoU matching can assign the operator's pose keypoints to the pedestrian's tracking box, causing the relation engine to misidentify the pedestrian as the operator!
  * **Occlusion Failure:** An operator inside a forklift cage has occluded knees and ankles. The pose model outputs near-zero confidence for lower limbs, leaving only shoulders and head visible.
* **Internal State:** Stateless feedforward model.
* **Dependencies:** PyTorch, Ultralytics pose weights.
* **Failure Modes:**
  * Total keypoint dropout in low lighting or deep shadow.
  * Skeleton jitter: Keypoints jittering by $\pm 10$ pixels frame-to-frame.
* **Confidence Metric:** Per-keypoint visibility confidence $\in [0, 1]$.
* **Fallback Behavior:** If IoU match $< 0.30$, `keypoints = None`.

### Layer 7: Operator-Vehicle Relation Engine

* **Module:** `core/operator_relation_v2.py` (`OperatorVehicleRelationEngineV2`)
* **Inputs:** `persons: List[Dict]`, `forklifts: List[Dict]`, `frame_idx: int`.
* **Outputs:** Pairwise relationship classifications: `OPERATOR_ON_VEHICLE`, `INDEPENDENT_PEDESTRIAN`, `UNKNOWN`.
* **Explicit Assumptions:**
  * An operator standing on an Electric Pallet Jack (EPJ) has torso inside the vehicle ROI $[0.3, 1.0] \times [0.2, 0.9]$ and ankles physically on the vehicle.
  * A person passing in front has ankles outside the vehicle box.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **CRITICAL MULTI-VEHICLE BUG:** In lines 246–253 of `operator_relation_v2.py`:
    The code iterates `for f in forklifts:`. If the relation is not `OPERATOR_ON_VEHICLE`, the loop finishes and only ONE relation is appended per person using `forklift_id: f["id"]`.
    If there are multiple forklifts (e.g. F1 and F2), the person's relation is recorded **only for the last forklift in the list**, and its evidence may belong to the first forklift! In a multi-forklift scene, relation checks against other forklifts return `None` (defaulting to `UNKNOWN`), corrupting safety decisions!
  * **Running Pedestrian Shortcut Flaw:** In `generate_v2_8_5_video.py` line 138:
    `p_is_op = (p_rel == "OPERATOR_ON_VEHICLE") or (p.get("speed_m_s", 0.0) > 0.8)`
    Any pedestrian walking briskly or running ($> 0.8$ m/s, where normal human walking is $1.4$ m/s) is classified as a vehicle operator!
* **Internal State:** `self._coupling_history: Dict[Tuple[int, int], List[int]]`, `self._frame_relations: Dict[int, List[Dict]]`.
* **Dependencies:** `math`, pose feature extraction helper.
* **Failure Modes:**
  * Multi-vehicle cross-contamination.
  * Fast pedestrians classified as vehicle operators.
  * Operator leaning out of cab classified as pedestrian.
* **Confidence Metric:** Discrete confidence score: $0.95$ (strong pose), $0.85$ (fallback), $0.50$ (unknown).
* **Fallback Behavior:** Defaults to `UNKNOWN` when cues conflict.

### Layer 8: Ground Plane & Metric Homography Engine

* **Module:** `core/geometry.py` (`GroundPlaneCalibrator`, `compute_metric_distance`)
* **Inputs:** Pixel coordinates `(x, y)` representing bottom-center ground contact points.
* **Outputs:** Metric ground plane coordinates $(X, Y)$ in meters; metric Euclidean distance in meters.
* **Explicit Assumptions:**
  * Ground is perfectly planar (2D plane $Z=0$).
  * The bottom-center of the 2D bounding box represents the true physical ground contact point.
  * Homography matrix $H$ accurately maps camera perspective to ground plane.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **Non-Ground Extrapolation:** The bottom-center of an operator standing on a raised platform or forklift cabin is NOT on the ground; it is 0.5m–1.0m above the floor. Projecting elevated points via ground homography causes **massive radial displacement errors (up to 3.0 meters of geometric distortion)**!
  * **Unvalidated Calibration:** `config/calibration/warehouse_test2.json` explicitly states: `"calibration_status": "VISUALLY_ESTIMATED_NOT_VALIDATED"`. Metric distances are approximations based on an assumed $8\text{m} \times 10\text{m}$ grid, not laser surveys.
* **Internal State:** Pre-computed $3 \times 3$ homography matrix $H$, inverse $H^{-1}$, convex hull of calibration points.
* **Dependencies:** OpenCV (`cv2.findHomography`, `cv2.perspectiveTransform`, `cv2.pointPolygonTest`).
* **Failure Modes:**
  * Elevated body parts projected far outside calibrated floor space.
  * Non-linear lens distortion (barrel/pincushion) near frame edges ignored by planar homography.
  * Division by near-zero homogeneous scale factor $w = h_{31}x + h_{32}y + h_{33}$ producing unphysical infinite coordinates.
* **Confidence Metric:** Spatial zone status: `INSIDE_CALIBRATION` (1.0), `EDGE_REGION` (0.0), `OUTSIDE_CALIBRATION` (0.0).
* **Fallback Behavior:** Distance returned as `None` if point falls outside convex hull.

### Layer 9: Trajectory & Kinematics Engine

* **Module:** `core/trajectory.py` (`TrajectoryEngine`, `WorldTrajectory`), `core/kinematics.py`
* **Inputs:** Time-series of metric positions $(X_t, Y_t)$, timestamps $t$.
* **Outputs:** Velocity vectors $(\dot{X}, \dot{Y})$, speed magnitude $v = \sqrt{\dot{X}^2 + \dot{Y}^2}$, displacement, trajectory length.
* **Explicit Assumptions:**
  * Frame timestamps are strictly increasing.
  * Trajectory points belong to the same physical entity over time.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * Smoothing window is fixed to 5 points. If frame rate drops or frames are dropped, the 5-point window spans an arbitrary time duration.
  * When an ID switch occurs, the trajectory engine links two distinct physical entities into a single trajectory, producing a momentary velocity spike of up to $20$–$50$ m/s ($180$ km/h).
* **Internal State:** List of `TrajectoryPoint` objects per track ID.
* **Dependencies:** NumPy, math.
* **Failure Modes:**
  * ID swap causes astronomical velocity spikes.
  * Detection jitter causes false high-frequency oscillation interpreted as high speed.
* **Confidence Metric:** None.
* **Fallback Behavior:** If $\Delta t \le 0$, returns velocity $(0, 0, 0)$.

### Layer 10: Metric TTC & Closest Point of Approach (CPA) Engine

* **Module:** `core/kinematics.py` (`compute_metric_ttc`) and `core/event_engine_v2.py` (inline TTC)
* **Inputs:** Positions $\mathbf{p}_p, \mathbf{p}_f$, velocities $\mathbf{v}_p, \mathbf{v}_f$, distance $d$.
* **Outputs:** `relative_velocity_m_s: float`, `ttc_sec: Optional[float]`, `ttc_status: str`.
* **Explicit Assumptions:**
  * Approaching objects are on a direct collision course.
  * $\text{TTC} = d / v_{\text{approach}}$.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **CRITICAL 1D RANGE-RATE FLAW (False Collision on Crossing Trajectories):**
    `compute_metric_ttc` computes approach velocity as:
    $$v_{\text{approach}} = \max(0.0, (\mathbf{v}_f - \mathbf{v}_p) \cdot \hat{\mathbf{r}})$$
    If a pedestrian walks across an aisle 5 meters ahead of an oncoming forklift, their distance $d(t)$ is momentarily decreasing ($v_{\text{approach}} > 0$).
    The engine computes a valid $\text{TTC} = d / v_{\text{approach}} < 3.0$s and triggers a collision alert, **even though the trajectories miss each other by 5 meters!**
    The system lacks a **Closest Point of Approach (CPA) / Miss-Distance filter**.
  * **Dual TTC Implementations:** There are two independent, conflicting TTC calculations:
    1. `core/kinematics.py`: Uses 2D velocity vectors.
    2. `core/event_engine_v2.py`: Uses 1D distance differences over a 5-frame window with a 66% monotonic step rule.
    These two modules can and do produce contradictory TTC estimates for the exact same event!
* **Internal State:** Stateless in `kinematics.py`; 15-frame history buffer in `event_engine_v2.py`.
* **Dependencies:** `math`.
* **Failure Modes:**
  * False collision alarms on safe, orthogonal crossing movements.
  * Div by zero / near-zero approach speeds yielding $TTC \to \infty$.
* **Confidence Metric:** Categorical status: `VALID`, `NO_APPROACH`, `UNDEFINED`.
* **Fallback Behavior:** Sets `ttc_sec = None` when $v_{\text{approach}} \le 0.1$ m/s.

### Layer 11: Risk Exposure Engine

* **Module:** `core/risk_engine.py` (`RiskEngine`), configured via `config/risk_weights.yaml`
* **Inputs:** `InteractionEvent` instance.
* **Outputs:** Continuous risk exposure score `total_exposure: float \in [0, \infty)`.
* **Explicit Assumptions:**
  * Risk decays exponentially with distance: $\text{Weight} \cdot e^{-\lambda \cdot d}$.
  * Risk scales linearly with interaction duration and time in danger/caution zones.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **SCHEMA INCOMPATIBILITY CRASH:** `RiskEngine.calculate_risk_exposure()` explicitly queries `event.median_distance_m` and `event.peak_approach_speed`.
    These fields exist in V2.0 `InteractionEvent`, but **DO NOT EXIST in V2.8 `InteractionEventV2`**!
    Passing an active `InteractionEventV2` to `RiskEngine` causes an unhandled `AttributeError`!
  * Because of this crash, `RiskEngine` was completely disconnected from the pipeline in V2.8.2, V2.8.3, V2.8.4, and V2.8.5!
* **Internal State:** Configuration dictionary loaded from YAML.
* **Dependencies:** PyYAML, math.
* **Failure Modes:**
  * Complete execution crash when passed V2.8 event objects.
  * Extreme sensitivity to exponential decay constant $\lambda = 1.5$.
* **Confidence Metric:** None.
* **Fallback Behavior:** Defaults missing distance to $10.0$m.

### Layer 12: Evidence & Quality Engine

* **Module:** `core/evidence.py` (`EvidenceEngine`)
* **Inputs:** `List[InteractionEvent]`, `total_video_frames`, `tracking_failures`.
* **Outputs:** `evidence_confidence: float \in [0, 1]`, `evidence_level: HIGH | MODERATE | LOW | INSUFFICIENT`, `limitations: List[str]`.
* **Explicit Assumptions:**
  * High track fragmentation ($>50\%$ of events $< 0.2$s) invalidates causal claims.
  * Tracking failure rate $>20\%$ indicates compromised sensor integrity.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * Like `RiskEngine`, `EvidenceEngine` expects V2.0 `InteractionEvent` structures.
  * Evidence confidence is calculated post-hoc at the video level, not frame-by-frame. A 5-minute video with flawless tracking for 4 minutes and massive failure in minute 5 is penalized globally.
* **Internal State:** Stateless.
* **Dependencies:** `core.event_engine.InteractionEvent`.
* **Failure Modes:**
  * Attribute errors on V2.8 event structures.
  * Arbitrary heuristic penalty values (e.g. subtracting $0.4$ for zero events, $0.3$ for fragmentation).
* **Confidence Metric:** Continuous score $[0.0, 1.0]$.
* **Fallback Behavior:** Returns `INSUFFICIENT` if confidence drops below $0.4$.

### Layer 13: Event Lifecycle Engine V2

* **Module:** `core/event_engine_v2.py` (`EventEngineV2`, `InteractionEventV2`)
* **Inputs:** Pairwise interactions `(person_id, forklift_id, distance_m, zone, relation)`.
* **Outputs:** `InteractionEventV2` objects with `event_state: CANDIDATE_EVENT | CONFIRMED_EVENT | SUPPRESSED_OPERATOR_EVENT`, `alert_state: NONE | PENDING | ALERTED | REVOKED`, `safety_state: SAFE | INSUFFICIENT_EVIDENCE`.
* **Explicit Assumptions:**
  * An event persists across tracking gaps up to `max_gap_frames = 15` ($0.6$ seconds).
  * An operator interaction must be suppressed (`SUPPRESSED_OPERATOR_EVENT`, `safety_state=SAFE`).
  * 3 consecutive confirmed frames promote alert from `PENDING` to `ALERTED`.
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **Contradictory Safety Semantics:** When an independent pedestrian enters the DANGER zone, line 135 sets:
    `self.event_state = "CONFIRMED_EVENT"`
    `self.safety_state = "INSUFFICIENT_EVIDENCE"`
    A confirmed dangerous pedestrian encounter is labeled as having insufficient safety evidence!
  * **State Value Conflation:** In line 175, when an event ends with zero risk frames, the code executes:
    `self.event_state = "INSUFFICIENT_EVIDENCE"`
    `self.safety_state = "SAFE"`
    This sets `event_state` (which should be an event lifecycle phase like `RESOLVED` or `CLOSED`) to a safety verdict string!
  * **Single-Pair Memory Coupling:** Keyed by `"P{pid}_F{fid}"`. If a person track swaps ID (e.g. P12 becomes P14), the event immediately closes and a new candidate event is born, fragmenting what was a continuous encounter.
* **Internal State:** `active_events: Dict[str, InteractionEventV2]`, `historical_events: List[InteractionEventV2]`.
* **Dependencies:** NumPy, math.
* **Failure Modes:**
  * Event fragmentation on track ID changes.
  * Semantic confusion between `event_state` and `safety_state`.
  * Premature closure if tracking drops for 16 frames.
* **Confidence Metric:** None explicit; relies on `alert_state` stages.
* **Fallback Behavior:** Event closed and archived to `historical_events`.

### Layer 14: Risk Redistribution & Counterfactual Engines

* **Module:** `core/redistribution.py`, `core/counterfactual.py`, `core/decision.py`
* **Inputs:** Segregated lists of `before_events` and `after_events`.
* **Outputs:** Spatial zone delta `risk_displaced: bool`, counterfactual deviation, final decision signal (`SAFETY_BACKFIRE`, `RISK_IMPROVEMENT`, `NO_SIGNIFICANT_CHANGE`).
* **Explicit Assumptions:**
  * Risk exposure generation is linear with respect to frame count.
  * Spatial zone shifting indicates risk displacement (the safety intervention backfired).
* **Hidden / Flawed Assumptions Discovered in Code:**
  * **Correlation Treated as Causation:** If risk in zone DANGER decreases while risk in zone CAUTION increases, `RiskRedistributionEngine` unconditionally declares: `"Risk was displaced to other zones."` It does not verify whether the entities in CAUTION were the same entities deflected from DANGER! A completely unrelated truck parking in CAUTION is falsely attributed as a "backfire displacement" of the intervention!
  * **Naive Rate Projection:** `CounterfactualEngine` assumes risk per 1,000 frames is constant. In reality, industrial warehouse activity is bursty, non-stationary, and governed by external logistics schedules.
* **Internal State:** Stateless.
* **Dependencies:** None.
* **Failure Modes:**
  * Spurious backfire verdicts caused by uncoupled background warehouse activity.
  * Division by zero if `before_frames == 0` or `after_frames == 0`.
* **Confidence Metric:** Heuristic scaling: `min(0.9, total_events / 50.0)`.
* **Fallback Behavior:** Returns `NO_STRONG_SIGNAL` if deviation is within $\pm 20.0$.

* **Module:** JSON export (`v2_9_baseline_runner.py`, `generate_v2_8_5_video.py`)
* **Inputs:** Complete in-memory state of events, tracks, and frames.

* **Dependencies:** Python standard `json` module.
* **Failure Modes:**

* **Confidence Metric:** Global pipeline confidence summary.
