# V3.0 CORE — Live Intelligence Architecture & Deep Redesign

## 1. Executive Summary & Problem Formulation

Following the V2.9 Forensic Audit, three fundamental architectural limitations were identified as structural bottlenecks preventing real-time, robust deployment:

1. **FAIL-08: Sequential Live Bottleneck**
   - In V2.9, frame processing was strictly sequential: Frame Decode $\to$ YOLO26n Detection $\to$ YOLOv8n Pose $\to$ TrackManager $\to$ Operator Relation $\to$ Kinematics $\to$ Event Engine.
   - Detection takes $\sim 21.5\text{ ms}$, while Pose takes $\sim 29.6\text{ ms}$.
   - Running both sequentially on every frame forced overall pipeline throughput to $\sim 15.8\text{ FPS}$ on Apple Silicon (MPS).
   - In a 25.0 or 29.97 FPS live RTSP stream, this created an escalating frame backlog and unbounded latency growth.

2. **FAIL-07: Event & Identity Fragmentation**
   - ByteTrack tracker IDs are ephemeral and unstable during multi-human occlusions, crossing trajectories, and rapid maneuvers.
   - In V2.9, interaction events were keyed directly to transient tracker IDs (`P{pid}_F{fid}`).
   - An ID switch (e.g. Track 10 $\to$ Track 11) abruptly terminated active safety encounters and spawned new candidate events, fragmenting audit logs and resetting time-to-collision accumulators.

3. **FAIL-10: Elevated-Camera Geometric Distortion**
   - Single-plane homography ($H$) maps 2D image coordinates to ground plane $Z=0$.
   - For an elevated forklift operator seated or standing $1.2\text{ m}$ above the floor, bottom bounding box contact points do not touch the ground.
   - Projecting elevated pixels via $H$ induced up to $2.2\text{ m}$ of radial distance distortion, generating false proximity alarms when vehicles were distant, and suppressing warnings when close.

**V3.0 Core delivers a complete analytical redesign resolving these three core failures while preserving the frozen V2.9 baseline for comparative auditability.**

## 2. Multi-Threaded Live Pipeline Architecture

The V3.0 Core decouples high-frequency detection/tracking from compute-heavy pose estimation and wraps all operations in strict timestamp contracts.

```text
RTSP / Video Ingest Thread
           │
           ▼
     [FramePacket] (frame_id, source_pts, capture_t, arrival_t)
           │
           ▼
    [Freshness Gate] ────(age > max_age)───► [FRAME DROP & LOG]
           │
           ▼
   [BoundedFrameQueue] (Max Size: 5, Backpressure Telemetry)
           │
           ▼
   Main Live Worker Thread (Full Source Rate: ~25-45 FPS)
   ┌────────────────────────────────────────────────────────┐
   │ 1. Detection & Tracking (YOLO26n + ByteTrack)           │
   │ 2. Conservative Durable Identity Layer (Entity IDs)     │
   │ 3. Non-blocking Pose Task Dispatcher (5/8/10 Hz Stride)│
   │ 4. Track Lifecycle & Safety Eligibility Gate            │
   │ 5. Pairwise Operator/Pedestrian Relation Engine         │
   │ 6. Empirical Ground Geometry (3D Vehicle Offset)        │
   │ 7. 2D CPA Miss-Distance & Metric TTC Calculation        │
   │ 8. Durable Event Engine V3 (Keyed by Entity Pair)       │
   └────────────────────────────────────────────────────────┘
           │                                 ▲
           ▼ (Non-blocking queue)            │ (Thread-safe cache)
   ┌──────────────────────────────┐          │
   │ Async Pose Worker Thread     │──────────┘
   │ (Stride: 8 Hz / 125 ms)      │
   │ Enforces PoseContract &      │
   │ Timestamp Monotonicity       │
   └──────────────────────────────┘
```

## 3. Microsecond Frame Contract (`FramePacket`)

In live safety systems, relying solely on sequential integer `frame_id` causes silent temporal drift under frame drops or variable network latency. Every frame entering V3.0 is packaged into an immutable `FramePacket` with 5 distinct temporal timestamps:

```python
class FramePacket:
    frame_id: int               # Sequential stream index
    image: np.ndarray           # Raw BGR image buffer
    source_timestamp: float     # Video PTS (Presentation Time Stamp)
    capture_timestamp: float    # Wall-clock sensor capture time
    arrival_timestamp: float    # Ingestion thread arrival time
    processing_timestamp: float # Worker thread start time
    completion_timestamp: float # Pipeline completion time
```

### Derived Latency Metrics
- **Queue Age**: $t_{\text{arrival}} - t_{\text{capture}}$
- **Processing Latency**: $t_{\text{completion}} - t_{\text{processing}}$
- **End-to-End Latency**: $t_{\text{completion}} - t_{\text{capture}}$

## 4. Freshness Policy & Bounded Queue

Safety intelligence prioritizes **decision freshness** over processing stale historical frames. Processing an old frame that arrived 500ms late produces a safety decision about the past, creating false reassurance during dynamic vehicle operations.

### Bounded Buffer Contract
- `BoundedFrameQueue` maintains a fixed capacity ($N = 5$ frames).
- When `capture_rate > processing_rate`, oldest buffered frames are evicted with recorded drop reason `Evicted due to queue overflow (Backpressure)`.
- If an ingested frame's `age_ms > max_allowed_age_ms` ($150.0\text{ ms}$), the `FreshnessPolicy` emits a `DROP` decision before GPU inference begins.

### Telemetry Tracked Per Minute
```json
{
  "queue_size": 1,
  "queue_max": 5,
  "total_enqueued": 250,
  "total_dequeued": 248,
  "total_dropped_overflow": 2,
  "total_dropped_stale": 0,
  "drop_rate_pct": 0.8
}
```

## 5. Asynchronous Pose Worker & Pose Timestamp Contract

### The Decoupled Stride Rationale
Human pose estimation is computationally expensive (~25-30ms on Neural Engine / MPS). However, human body posture, bounding box foot contact, and operator seat occupancy do not change drastically within 40ms (25 Hz). Running pose at **8 Hz** (every 125ms) maintains full safety awareness while freeing 68% of the GPU compute budget for detection and trajectory extrapolation.

### Strict `PoseContract`
Pose estimates must never silently propagate into newer frames without explicit staleness metadata:

```python
class PoseContract:
    pose_id: str
    pose_frame_id: int
    pose_timestamp: float
    source_track_id: int
    source_entity_id: str
    keypoints: List[List[float]] # [x, y, confidence] x 17
    keypoint_confidence: float
```

### Staleness State Machine
1. **`FRESH_POSE`** ($\Delta t \le 150\text{ ms}$, $\Delta \text{frames} \le 5$):
   - Fully eligible for posture classification, ankle footpoint ground projection, and operator seat verification.
2. **`STALE_POSE`** ($150\text{ ms} < \Delta t \le 400\text{ ms}$):
   - Ineligible for new safety state promotions; triggers confidence degradation in ground projection.
3. **`UNAVAILABLE_POSE`** ($\Delta t > 400\text{ ms}$ or low confidence):
   - Safety engine falls back to bounding box kinematics and degrades ground position confidence.

## 6. Worker Ordering Integrity & Monotonicity Invariant

A major hazard in multi-threaded vision pipelines is out-of-order state overwrites:
```text
Detection Worker: Frame 100 ──► Frame 101 ──► Frame 102
Pose Worker:      Pose(100) ──────────────► Pose(102) ──► Pose(101 [delayed])
```
If the delayed pose from Frame 101 overwrote the entity state after Frame 102 was processed, the entity would experience time reversal.

### The Monotonicity Invariant
In `AsyncLivePipeline`:
```python
existing = self.latest_pose_by_entity.get(entity_id)
if existing is None or incoming_pose.pose_frame_id >= existing.pose_frame_id:
    self.latest_pose_by_entity[entity_id] = incoming_pose
else:
    # REJECT late result; log out-of-order drop
    pass
```
Validated by `test_worker_ordering_integrity()`: late worker results are rejected and cannot corrupt newer frames.
