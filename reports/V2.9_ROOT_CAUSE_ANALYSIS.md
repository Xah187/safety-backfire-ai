# V2.9 — Root Cause Analysis (RCA) Report

**Document Version:** 2.9.0-RCA  
**Methodology:** 5-Whys Causal Chains, Fault Tree Analysis, Propagation Mapping  
**Scope:** Exhaustive investigation of Critical (P0) and High (P1) failure modes discovered during V2.9 Red-Team audit.

---

## 1. Executive Root Cause Summary

The forensic investigation revealed that Safety Backfire AI's past failure modes were **not** merely peripheral detector errors (e.g. YOLO misdetections or ByteTrack glitches). Instead, the system suffered from **deep structural contradictions between layers**:
1. **Multi-Vehicle Scope Contamination:** The relation engine dropped associations for all vehicles except the last one in the frame due to loop variable overwrite.
2. **Missing Closest Point of Approach (CPA) Geometry:** Range-rate TTC assumed any decreasing distance was a collision, causing false emergency alerts on safe orthogonal crossings.
3. **Overly Restrictive Anthropometric Heuristics:** The observation gate assumed all humans are upright cylinders, erasing fallen and crawling workers ("Man Down").
4. **Inter-Module Schema Desynchronization:** V2.8 rewritten data contracts severed compatibility with the `RiskEngine`, leaving it completely inoperable.
5. **Heuristic Semantic Shortcuts:** Speed thresholds ($>0.8$ m/s) bypassed relation verification, misclassifying running workers as forklift operators.
6. **Sequential Inference Bottleneck:** Running Detector and Pose sequentially on every frame capped throughput at 15.5 FPS, making live 25 FPS stream processing impossible without frame latency accumulation.

## 2. In-Depth Root Cause Analysis (P0 & P1 Failures)

---

### [RCA-01] Multi-Vehicle Relation Overwrite & Association Dropout

* **Discovered Issue:** In `OperatorVehicleRelationEngineV2.classify_frame`, relations in scenes with 2 or more forklifts were either completely lost or assigned to the wrong vehicle ID.
* **5-Whys Analysis:**
  1. *Why was the relation for Forklift 1 missing when queried?* Because `get_person_relation(person_id, forklift_1_id)` returned `None`.
  2. *Why did it return `None`?* Because `self._frame_relations` only contained an entry for `forklift_2_id`.
  3. *Why was Forklift 1 omitted from `_frame_relations`?* Because `relations.append()` was located outside the inner `for f in forklifts:` loop.
  4. *Why was it placed outside the loop?* The original developer assumed a person can only interact with one vehicle at a time and attempted to select the "best" relation across the loop.
  5. *Why did that cause a bug?* In Python, the loop variable `f` retains the value of the **last iteration**. When the loop finished, `relations.append({"forklift_id": f["id"], ...})` used the ID of the last forklift, while `best_evidence` was captured from an earlier forklift.
* **Trigger:** Any scene with $\ge 1$ person and $\ge 2$ forklifts.
* **Affected Modules:** `core/operator_relation_v2.py`, `core/event_engine_v2.py`, all downstream safety alerts.
* **Why Existing Safeguards Failed:** Unit tests only instantiated 1 Person + 1 Forklift. Multi-vehicle scenes were never tested with assertions on both vehicle IDs.
* **Recommended Fix:** 
  - Restructure `classify_frame` to record a distinct relation dictionary for **every valid person-forklift pair** `(p["id"], f["id"])`.
  - Provide a dedicated lookup `get_person_relation(person_id, forklift_id, frame_idx)` that indexes by `(person_id, forklift_id)`.
* **Regression Risk:** Low. Fix aligns data structure with pairwise matrix semantics.

### [RCA-02] 1D Range-Rate TTC False Collisions on Crossing Paths

* **Discovered Issue:** When a pedestrian crosses an aisle 5 to 10 meters ahead of a traveling forklift, `compute_metric_ttc` reports `VALID` and emits TTC $< 3.0$s, even though the trajectories miss each other by $> 5$ meters.
* **5-Whys Analysis:**
  1. *Why was an impending collision flagged?* Because `ttc_sec` was calculated as $< 3.0$s with status `VALID`.
  2. *Why was TTC calculated when objects do not collide?* Because the formula used was $\text{TTC} = d / v_{\text{approach}}$, where $v_{\text{approach}} = \max(0, \mathbf{v}_{\text{rel}} \cdot \hat{\mathbf{r}})$.
  3. *Why was $v_{\text{approach}} > 0$ when they were not colliding?* Because when two objects travel on orthogonal paths, the Euclidean distance between them decreases before increasing.
  4. *Why did the system interpret distance reduction as an impending collision?* The system lacked a 2D trajectory projection model to determine the **Closest Point of Approach (CPA)**.
  5. *Why was CPA omitted?* The module was designed as a 1D range-rate proxy carried over from early automotive radar concepts without spatial miss-distance validation.
* **Trigger:** Pedestrian walking across an intersection while a forklift approaches from the side.
* **Affected Modules:** `core/kinematics.py`, `core/event_engine_v2.py`.
* **Why Existing Safeguards Failed:** Historical tests only tested head-on collinear trajectories where 1D distance reduction accurately predicts impact.
* **Recommended Fix:**
  - Implement vector-based Closest Point of Approach (CPA) calculation:
    $$t_{\text{cpa}} = -\frac{\mathbf{r}_0 \cdot \Delta\mathbf{v}}{\|\Delta\mathbf{v}\|^2}$$
    $$\mathbf{r}_{\text{cpa}} = \mathbf{r}_0 + \Delta\mathbf{v} \cdot t_{\text{cpa}}$$
    $$\text{Miss-Distance} = \|\mathbf{r}_{\text{cpa}}\|$$
  - TTC is ONLY valid if $t_{\text{cpa}} > 0$ **AND** $\text{Miss-Distance} \le \text{Safety Radius}$ ($1.5$m for warehouse vehicle).
* **Regression Risk:** Very Low. Drastically suppresses false alarms on orthogonal crossings without affecting true head-on or tail-gating hazards.

### [RCA-03] Anthropometric Aspect Ratio Gate Erasing Fallen Workers ("Man Down")

* **Discovered Issue:** A worker lying on the floor (aspect ratio $\text{height}/\text{width} = 0.44 < 1.0$) is classified as `INVALID` and rejected from safety eligibility.
* **5-Whys Analysis:**
  1. *Why was the fallen worker ignored by the safety system?* Because `safety_eligible` was set to `False`.
  2. *Why was safety eligibility revoked?* Because `ObservationIntegrityGate` returned `ObservationValidity.INVALID`.
  3. *Why was the observation declared INVALID?* Rule 3 checked: `if aspect_ratio < self.min_human_aspect (1.0): return INVALID`.
  4. *Why was minimum aspect ratio set to 1.0?* To reject wide, horizontal forklift chassis hallucinations and tire reflections.
  5. *Why was no exception made for human bodies?* The gate failed to decouple an upright standing human from a recumbent human, assuming all valid humans must be vertical cylinders.
* **Trigger:** Worker slips, trips, falls, or faints in the warehouse aisle.
* **Affected Modules:** `core/observation_gate.py`, `core/track_manager.py`.
* **Why Existing Safeguards Failed:** Previous gate validation (V2.8.5) focused exclusively on standing workers and upright vehicle chassis hallucinations.
* **Recommended Fix:**
  - Decouple horizontal blobs into:
    - **Tire/reflection artifacts:** Very low aspect ratio ($<0.5$), zero keypoints, rigid ground-plane coupling with vehicle.
    - **Man Down candidate:** Non-zero human confidence from detector head, ground contact, spatial context away from vehicle chassis, or temporal history of having previously stood.
  - If a detection is classified as `person` with high confidence ($>0.60$) on the floor, mark as `WEAK` (`safety_eligible = True`) with reason `man_down_candidate`, rather than erasing it as `INVALID`.
* **Regression Risk:** Low. Must ensure bulky forklift chassis hallucinations on the vehicle body remain filtered via `spatial_context["vehicle_overlap"]`.

### [RCA-04] Complete System Crash in RiskEngine on EventEngineV2

* **Discovered Issue:** Calling `RiskEngine.calculate_risk_exposure()` raises `AttributeError: 'InteractionEventV2' object has no attribute 'median_distance_m'`.
* **5-Whys Analysis:**
  1. *Why does calling RiskEngine crash the application?* Python throws an unhandled `AttributeError`.
  2. *Why does the attribute not exist?* `InteractionEventV2` only implements `min_distance_m`, `distances_m`, and `smoothed_distance_m`.
  3. *Why did RiskEngine query `median_distance_m`?* `RiskEngine` was written in Phase 2 for V2.0 `InteractionEvent`, which calculated median distance in `end()`.
  4. *Why was `median_distance_m` dropped from `InteractionEventV2`?* During the V2.8 rewrite to support the Safety Matrix, `InteractionEventV2` was created as a new class without backward-compatible attribute parity.
  5. *Why was this not caught in V2.8 testing?* The V2.8 and V2.8.2 experiment scripts omitted `RiskEngine` completely and only rendered visual bounding boxes, leaving the engine unexecuted.
* **Trigger:** Any invocation of `RiskEngine` on V2.8+ events.
* **Affected Modules:** `core/risk_engine.py`, `core/event_engine_v2.py`.
* **Why Existing Safeguards Failed:** Test suites in `tests/test_risk_engine.py` only tested mock V2.0 objects, never V2.8 objects.
* **Recommended Fix:**
  - Add attribute compatibility to `InteractionEventV2`:
    - Compute `median_distance_m = float(np.median(self.distances_m))` in `end()`.
    - Compute `peak_approach_speed` from kinematics history.
  - Update `RiskEngine` to safely query attributes via `getattr(event, 'median_distance_m', None)`.
* **Regression Risk:** Zero. Restores intended functionality.

### [RCA-05] Running Pedestrian Falsely Suppressed as Operator via Speed Shortcut

* **Discovered Issue:** In `generate_v2_8_5_video.py`, pedestrians walking briskly or running ($> 0.8$ m/s) are labeled as `OPERATOR ON MOVING FORKLIFT` and suppressed from safety alerts.
* **5-Whys Analysis:**
  1. *Why was a running pedestrian suppressed near a parked forklift?* Because `p_is_op` was `True`, triggering `if p_is_op and not f_is_moving: continue`.
  2. *Why was `p_is_op` evaluated as `True`?* Because line 138 evaluated: `p_is_op = (p_rel == "OPERATOR_ON_VEHICLE") or (p.get("speed_m_s", 0.0) > 0.8)`.
  3. *Why was `speed > 0.8` used to declare someone an operator?* To handle cases where a forklift detection box flickered off while an operator was riding an EPJ.
  4. *Why is `0.8 m/s` invalid for this purpose?* Average adult human walking speed is $1.3$–$1.4$ m/s; brisk walking is $1.7$ m/s; running exceeds $2.5$ m/s. Any unimpeded pedestrian easily exceeds $0.8$ m/s.
  5. *Why was speed alone treated as vehicle operation?* The script used an ad-hoc heuristic without requiring spatial proximity to a vehicle.
* **Trigger:** Any pedestrian walking at normal or brisk speed.
* **Affected Modules:** `generate_v2_8_5_video.py`, downstream proximity filters.
* **Why Existing Safeguards Failed:** `test2.mp4` contains only one visible human (who happens to be riding the EPJ), so the heuristic appeared to work on this single video.
* **Recommended Fix:**
  - Eliminate the standalone `speed > 0.8` shortcut.
  - An entity can only be an operator if:
    1. `p_rel == "OPERATOR_ON_VEHICLE"` (verified by Pose ROI/coupling), OR
    2. Motion speed matches a specific co-located forklift ($|\mathbf{v}_p - \mathbf{v}_f| < 0.3$ m/s with 2D IoU $> 0.3$).
* **Regression Risk:** Low. Prevents dangerous false negatives for moving pedestrians.

### [RCA-08] Pipeline Latency & Sequential Inference Bottleneck

* **Discovered Issue:** End-to-end processing throughput on current Mac hardware is **15.5 FPS**, preventing real-time 25 FPS live streaming.
* **5-Whys Analysis:**
  1. *Why does the pipeline run at 15.5 FPS instead of 25+ FPS?* Total frame latency is $64.5$ms ($1 / 0.0645 = 15.5$ FPS).
  2. *Where is the $64.5$ms spent?*
     - Detector (`YOLO26n`): $33.5$ms ($41.7$s / 1246 frames).
     - Pose Estimator (`YOLOv8n-pose`): $29.6$ms ($36.9$s / 1246 frames).
     - Everything else (Tracking, Geometry, Logic): $< 1.5$ms total!
  3. *Why is Pose taking 29.6ms per frame?* Because `pose_model.predict(frame)` is executed on the full 640x640 frame sequentially after detection.
  4. *Why is it executed on every single frame?* The pipeline architecture runs synchronous, frame-by-frame inference without temporal decimation or asynchronous threading.
  5. *Can the pipeline process live RTSP at 25 FPS in this architecture?* **No.** In synchronous mode, the system will fall behind real-time by $\approx 380$ms every second ($10$ seconds of lag every $26$ seconds).
* **Recommended Architectural Remedy (for V3.0 Core):**
  - Decouple Pose from the 25 FPS critical loop: Run Pose asynchronously or at a reduced stride (e.g. every 3rd or 4th frame), interpolating keypoints via ByteTrack Kalman state.
  - Crop-based pose: Run pose only on cropped person bounding boxes rather than the full 640x640 frame.
* **Regression Risk:** Requires asynchronous architecture redesign; documented as a core finding for next engineering phase.
