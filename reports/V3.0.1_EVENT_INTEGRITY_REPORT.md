# V3.0.1 Event Episode Integrity & Safety Provenance Report

## Executive Summary

The Event Engine is the final safety arbiter of the Safety Backfire AI system. While upstream layers classify pixels and tracks, the Event Engine constructs stateful safety episodes, dispatches proximity alerts, and logs safety audit trails.

In V3.0.1, the Event Engine was red-teamed against **Episode Collision (`FAIL-17`)**, **Illegal State Machine Transitions (`FAIL-20`)**, **Cross-Pair Evidence Contamination**, and **Broken Lineage Graphs**.

---

## 1. Episode vs. Entity Pair Decoupling (`FAIL-17`)

### The Architecture Flaw Identified (`FAIL-17`)
In V3.0 Core, event episodes were keyed directly by the tuple `(person_entity_id, forklift_entity_id)`.
- **Failure Manifestation**: If worker `P_ENT_0001` approached forklift `F_ENT_0001` at frame 100, an event was opened and later closed at frame 110. When the same worker approached the same forklift at frame 500 (2 minutes later in real time), the engine attempted to reuse the existing episode object or collided with the closed record.
- **Safety Violation**: Historical safety audits require each distinct interaction episode to possess an immutable, globally unique identifier.

### The Decoupling Fix
In V3.0.1, event episodes are identified by a sequential, globally unique episode key:
$$\text{Episode ID} = \texttt{EPISODE\_}\{\text{counter}\}\texttt{\_\_}\{\text{person\_entity}\}\texttt{\_vs\_}\{\text{forklift\_entity}\}$$

### Empirical Verification (`test_event_episode_adversarial.py`)
```text
Episode 1 closed with Event ID: EPISODE_0001__P_ENT_0001_vs_F_ENT_0001 (Frames 100-110)
Episode 2 initialized with Event ID: EPISODE_0002__P_ENT_0001_vs_F_ENT_0001 (Frame 500)
[PASS] Episode 1 and Episode 2 have distinct episode IDs for identical entity pair.
```
- **Result**: **Resolved**. The same entities engaged in sequential, distinct near-misses produce fully isolated, non-colliding episodes.

## 2. Illegal State Machine Transition Audit (`FAIL-20`)

The Event state machine was tested against an adversarial transition matrix to identify prohibited state regressions:

```
+---------------------------------------------------------------------------------------------------+
|                              EVENT STATE TRANSITION FIREWALL                                      |
|                                                                                                   |
|  [ CANDIDATE ] ───(Confirm)───> [ CONFIRMED ] ───(Alert)───> [ ALERTED ] ───(End)───> [ CLOSED ]  |
|         ^                             |                             |                    |        |
|         |                     (Distance Widen)                (Distance Widen)           |        |
|         |                             v                             v                    |        |
|         +─── [FORBIDDEN REGRESSION] ──+─────────────────────────────+                    X        |
|                                                                                    (IMMUTABLE)    |
+---------------------------------------------------------------------------------------------------+
```

### Prohibited Transition Audit Table
| Prohibited State Transition | Adversarial Attack Injected | Expected Engine Behavior | Observed Behavior | Audit Verdict |
| :--- | :--- | :--- | :--- | :--- |
| **Confirmed $\to$ Candidate** | Distance widens temporarily | Lock in Confirmed; transition to Closing | State maintained `CONFIRMED_EVENT` | **PASS (Regressions blocked)** |
| **Alerted $\to$ Silently Removed** | Tracker temporarily skips 1 frame | Hold alert buffer; require explicit decay | State maintained `ALERTED` | **PASS (Hysteresis held)** |
| **Closed $\to$ Confirmed / Reopened** | Late frame arrives for ended event | Reject update with `RuntimeError` | Exception raised: `Cannot update closed event` | **PASS (`FAIL-20` Resolved)** |
| **Suppressed $\to$ Alerted** | Operator seated in cab | Require operator dismount confirmation | Alert strictly suppressed | **PASS (Suppression invariant held)** |

*Resolution of `FAIL-20`*: In V3.0, late-arriving asynchronous results could mutate closed event records ("Zombie Updates"). V3.0.1 implements an immutable state guard: calling `update()` on an event in `ENDED` status immediately raises a safety exception.

## 3. Pair Contamination & State Leakage Audit

### Multi-Agent Cross-Interaction Test
Two simultaneous worker-forklift pairs were simulated in the same physical zone:
- **Pair 1**: Worker `P01` interacting with Forklift `F01` (Critical proximity, distance $1.2\,\text{m}$, TTC $1.1\,\text{s}$).
- **Pair 2**: Worker `P02` interacting with Forklift `F02` (Safe perimeter, distance $6.5\,\text{m}$, TTC $8.0\,\text{s}$).

During the interaction, `P01` and `P02` cross paths, inducing tracker ID switches (`P01`: 10 $\to$ 11, `P02`: 20 $\to$ 21).

### Contamination Audit Measurements
| Measured Parameter | Pair 1 (`P01` + `F01`) | Pair 2 (`P02` + `F02`) | Cross-Leakage Observed? |
| :--- | :--- | :--- | :--- |
| **Event State** | `CONFIRMED_EVENT` | `CANDIDATE_EVENT` (Unconfirmed) | **NONE** |
| **Alert Dispatch** | `ALERTED` (Active Siren/Brake) | `NORMAL` (Zero alert) | **NONE** |
| **Track Lineage History** | Track IDs: `[(10, 1), (11, 1)]` | Track IDs: `[(20, 1), (21, 1)]` | **NONE** |
| **Kinematic Feature Set** | Min Distance: $1.20\,\text{m}$ | Min Distance: $6.48\,\text{m}$ | **NONE** |

*Verification*: Zero cross-pair state leakage occurred. The absorption of tracker ID switches by the Identity Layer maintained strict pair isolation.
